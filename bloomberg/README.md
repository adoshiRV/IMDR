# `bloomberg/` — BBG Terminal Code

## Purpose

The **sole purpose** of this folder is to **download fresh data from Bloomberg Terminals** and drop it into a shared cache that the IMDR ingest side watches and appends to the database.

```
  ┌────────────────────────┐       ┌────────────────────────┐       ┌──────────┐
  │ BBG user (DS/RM/RW/SP) │  ───▶ │   shared snapshot cache │ ───▶ │ IMDR DB  │
  │ runs script on their   │       │   (parquet, per-user,   │       │ (append) │
  │ Terminal-logged device │       │   timestamped)          │       │          │
  └────────────────────────┘       └────────────────────────┘       └──────────┘
        producer (here)                  drop zone                    consumer
                                                                  (IMDR watcher,
                                                                   already exists)
```

- **Producer = this folder.** Code here only knows how to talk to the Terminal and write snapshots to the cache. It never touches the DB directly.
- **Consumer = IMDR.** A separate IMDR job (hourly or filesystem-watch) scans the cache, picks up new/changed files, and appends to the DB.
- **The split exists** because only the user's machine has a logged-in Terminal session — the DB-writing pipeline runs elsewhere and can't `blpapi` itself.

This folder is **distinct** from:

- `Z:\...\BBG\`, `Z:\...\BBG_ASIA\`, `Z:\...\BBG_mirror\` — read-only output of the external R pipeline. Never write there.
- `src/imdr/vendors/` — the framework-level BBG file-share ingest (consumer side of the R pipeline).
- `playground/` — exploratory, throw-away scripts.
- `scripts/` — scheduled production ingest jobs and the cache watcher.

## Rules

### 1. Sole job: pull from Terminal, write to cache
- A script in `bloomberg/{user}/` **only** does two things:
  1. Issue `blpapi` (or equivalent) requests against the logged-in Terminal.
  2. Write the response to the shared snapshot cache.
- **No DB writes from here.** No `mssql.py`, no SQLAlchemy. The IMDR watcher owns ingestion.
- No transformations beyond what's needed to make the snapshot useful (parsing the BBG response into a tidy parquet is fine; computing analytics is not).

### 2. Runs on 4 user devices
- Same scripts must work unchanged on all four users' machines. No machine-specific paths or hard-coded user names — derive `{user}` from the folder the script lives in, or from a CLI flag / env var.
- Local Python env on each device must have `blpapi` installed and a logged-in Terminal.
- Shared cache path must be reachable from all four devices **and** from the IMDR consumer host.

### 3. Three cadences — Daily, Hourly, Snapshot

| Mode         | When it fires                           | What it pulls                                                       | How triggered                                  |
| ------------ | --------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------- |
| **Daily**    | Once per day (post-close)               | Only rows tagged `schedule=daily` for this user                     | Windows Task Scheduler entry                   |
| **Hourly**   | Every hour during market hours          | Only rows tagged `schedule=hourly` for this user                    | Windows Task Scheduler entry                   |
| **Snapshot** | On-demand — "hit refresh, give me everything" | **Every enabled row** for this user (daily + hourly + snapshot-tagged) | User runs the CLI (or a desktop shortcut)      |

Rows tagged `schedule=snapshot` are pulled **only** when the user invokes Snapshot mode. Rows tagged `daily`/`hourly` are pulled both on their schedule **and** on every Snapshot. This way the on-demand refresh always returns the user's full view; no need to remember a separate ticker list per cadence.

Each run is a full pull for that mode's ticker set — not incremental — so a missed hour is self-healing on the next run.

### 4. Central ticker lists — `bloomberg/tickers/` (3 split files + universe)

The firm-wide ticker registry is **split by domain** so each file carries the natural schema for its category. No empty-cell coercion, and each domain joins to its own downstream fact table.

```
bloomberg/
├── tickers/                     ← source of truth (the producer reads these)
│   ├── rates.csv                  IRS / OIS / BASIS / CCS swap PAR points
│   ├── bonds.csv                  GOVT / LINKER bond yields + BEI
│   └── fx.csv                     FX SPOT + forward points
├── tickers_universe.csv         ← auto-derived denormalised reference (do NOT edit)
└── bbg_mirror_inventory.csv     ← raw BBG_mirror dump (regenerated by playground/bloomberg/scan_bbg_mirror.py)
```

Each row is assigned to a `user` (the terminal it runs against) and a `schedule` (which orchestrator slot picks it up). The `domain` is **not** a column inside the split files — it's injected by [refresh.py](refresh.py) at load time based on which file the row came from (`tickers/rates.csv` → `domain=rates`, etc.). This way the file name is the source-of-truth for routing and stays in lockstep with the downstream sweeper.

#### Per-file schemas

| File | Columns | Notes |
|---|---|---|
| `tickers/rates.csv` | `ticker, user, fields, schedule, enabled, owner, currency, kind, curve_code, tenor, notes` | `kind ∈ {IRS, OIS, BASIS, CCS}`. For BASIS/CCS, `currency` is the non-USD leg (e.g., `CNH`); `curve_code` is the full pair-encoded form (`CNH-FIXED.USD-SOFR-ON`). |
| `tickers/bonds.csv` | `+ country, issuer_class, quote_type` | `quote_type ∈ {YIELD, BREAKEVEN, PRICE}`. `issuer_class` is `SOVEREIGN` (default) or `AGENCY` (e.g., `CNY_CDB_NOMINAL_GENERIC`). `country` is ISO-3 (USA, GBR, DEU, …). |
| `tickers/fx.csv` | `ticker, user, fields, schedule, enabled, owner, ccy, country, tenor, notes` | `ccy` is the non-USD leg (e.g., `JPY` for `JPY curncy`, `AUD` for `AUD1W curncy`). Spot rows have `tenor=SPOT`; forwards `1W / 1M / 3M / …`. |

#### `tickers_universe.csv` — reference view

Auto-derived denormalised union across the 3 split files. **Reference only — never edited directly, never read by `refresh.py`.** Columns: `ticker, user, schedule, enabled, owner, domain, kind, currency, country, curve_code, tenor, quote_type, source_file`. Use it to grep across categories ("show me all 10Y tickers", "every JPY ticker we pull"). Regenerated by the same splitter that produces the 3 files.

#### Adding tickers

1. Open the right file — `tickers/rates.csv` for swaps, `tickers/bonds.csv` for bonds, `tickers/fx.csv` for FX.
2. Add the row with the file's full schema.
3. Run `python -m playground.bloomberg.rebuild_universe` to refresh `tickers_universe.csv`.
4. Commit the split file + the regenerated universe.
5. The next scheduled run for that user/schedule picks it up.

#### How `refresh.py` consumes them

The shared orchestrator [refresh.py](refresh.py) walks all 3 files, filters to `--user X --schedule Y` (or every enabled row for `--schedule snapshot`), and concatenates. Each row carries its file's domain-specific columns plus an injected `domain` field. The downstream snapshot CSV preserves `domain` so the IMDR sweeper can route each row to the right fact table.

### 6. Cache output
- **Location**: `data/bloomberg/{user}/...` under the repo root. The repo lives on `Z:\` which all four user PCs already have write access to (the R BBG pipeline writes from these same PCs), so this path is automatically shared across producers + the IMDR consumer host. `data/*` is gitignored — only code + the `tickers/` directory + `tickers_universe.csv` go into git.
- **Format**: CSV for now (refresh runner + smoke test). Parquet later for high-volume jobs.
- **Filename**: `bbg_{schedule}_{YYYYMMDD}_{HHMMSS}.csv` (refresh) / `smoke_test_{YYYYMMDD}_{HHMMSS}.csv`. Seconds-level timestamp eliminates collisions if a previous run is stuck and the next scheduled run overlaps.
- **Schema**: long format — one row per (ticker, field). Columns: `ticker, terminal_user, pulled_at_utc, host, domain, field, value`. The dedupe key on the IMDR side is `(ticker, pulled_at_utc, terminal_user, field)`.
- **Atomicity**: write to `*.tmp`, then rename. Partial files must never be visible to the watcher.

### 7. Reusable helpers
- Shared logic lives at the top of `bloomberg/` (e.g. [refresh.py](refresh.py), [smoke_test.py](smoke_test.py)).
- The per-user folders (`dsuri/`, `rmahadevan/`, …) are currently empty — they exist so user-specific overrides can land there later if needed, and so the cache-write convention has a stable target.
- Anything used outside this folder (e.g. by the IMDR consumer or the email formatter) belongs in `src/imdr/`, not here.

### 8. Don't ship secrets or large output
- No `.bbcfg`, session tokens, or terminal credentials in commits.
- The snapshot cache itself stays out of git — only the **code**, the **`tickers/`** directory, and the auto-generated **`tickers_universe.csv`** are committed.

### 9. Safety
- Read-only Terminal calls only. No order/trade/upload actions.
- Respect Bloomberg API caps (`ReferenceDataRequest` / `HistoricalDataRequest` daily limits) — log usage; back off on failures.
- A failed run should leave the cache untouched (no half-written file, no stale-but-renamed file).

All scripts in this folder run inside the **`imdrbbg`** conda env, defined in [environment.yml](environment.yml). Slim by design: `python 3.11 + blpapi + pyarrow + pyyaml + jinja2 + python-dotenv + pywin32 + structlog`. Distinct from the full `imdr` developer env. `jinja2` + `pywin32` + `python-dotenv` + `structlog` are there so the refresh runner can send Outlook summary emails via IMDR's existing notifications system.

## Refresh runner — the real driver

**Command Prompt / PowerShell** (same commands after `conda init`):
```cmd
conda activate imdrbbg

:: Scheduled — runs from Task Scheduler (all 3 domains for this user)
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule daily
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule hourly

:: On-demand — user runs this from a shortcut
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule snapshot

:: App-driven — scope to a single domain
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule snapshot --domain fx
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule snapshot --domain rates
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule snapshot --domain bonds

:: Useful flags
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule hourly --dry-run
python Z:\Business\Personnel\Arjun\GitHub\IMDR\bloomberg\refresh.py --user dsuri --schedule hourly --no-email
```

**`--domain` filter** — optional, one of `rates / bonds / fx`. Omit to pull
all three (scheduled-run default). Use it for app-driven invocations to
keep request size small and stay clear of the BBG per-request soft cap.

What it does on every run:
1. Loads all 3 ticker files (`tickers/rates.csv`, `tickers/bonds.csv`, `tickers/fx.csv`), filters each to enabled rows for `--user` and `--schedule` (Snapshot mode pulls every enabled row regardless of `schedule` column), and concatenates. The `domain` for each row is set from its source file.
2. Issues one `ReferenceDataRequest` for all matching (ticker × field) pairs. ⚠️ **Known limit**: a single `ReferenceDataRequest` carrying ≳500 securities risks partial responses or `responseError` from `//blp/refdata`. At today's daily count (≈800) the request will need chunking before it can run reliably. See "Open design issues" below.
3. Writes `data/bloomberg/{user}/bbg_{schedule}_{YYYYMMDD}_{HHMMSS}.csv` (atomic via `.tmp` rename). The output schema is unchanged from the pre-split era: `ticker, terminal_user, pulled_at_utc, host, domain, field, value`. Domain-specific source columns (e.g., `curve_code`, `quote_type`) are **not** carried into the snapshot — the sweeper consumer joins back to `tickers/{rates,bonds,fx}.csv` for routing context.
4. Sends a summary email via the existing IMDR notifications system:
   - Subject: `[IMDR] Bloomberg Terminal — Daily|Hourly|Snapshot Refresh OK|PARTIAL|FAIL | {user} | n_ok/n_total tickers | YYYY-MM-DD HH:MM UTC`
   - Body: full snapshot table + any errors, with a green/orange/red banner.

Email recipient comes from `IMDR_EMAIL_TO` in the repo `.env`; gated by `IMDR_EMAIL_ENABLED=true`. If either is missing the run prints to stdout and exits normally — email is best-effort, never blocks the data pull.

Scheduled use: one Windows Task Scheduler entry per `(user, schedule)` pair on each user's PC. Snapshot mode is **never** scheduled — only run manually.

## Consumer-side reminders (out of scope for this folder)

- IMDR scanner runs every ~15 minutes, picks up new files in `data/bloomberg/{user}/`, appends to the DB.
- Idempotency key: `(ticker, pulled_at_utc, terminal_user, field)`.
- Files older than ~1 week get pruned by a separate weekly job — the DB is the system of record.

## Open design issues

- **`ReferenceDataRequest` batching** — [refresh.py](refresh.py) currently sends one request with every security appended. At today's daily count (≈800) this risks partial responses. Needs a chunked-loop (~200 securities per request, merge responses) before the full ticker set is enabled. App-driven callers can work around this today by passing `--domain` to scope down.
- **Per-user domain ownership** — design intent is that a given terminal user owns a subset of domains (e.g., DS pulls rates, RW pulls FX). Today this is implicit in which rows have which `user` value across the 3 files. May want to make it explicit via a small `bloomberg/tickers/assignments.csv` or a column comment, so misassignments are easier to spot.
- **`--ticker` (ad-hoc one-shot list)** — there's no way today to pull a single ticker or short list without editing the CSVs. Probably not worth adding until a use case appears.
- **Watcher trigger** — 15-minute poll (default) vs `watchdog` push? Polling is more robust on SMB; revisit if latency matters.
- **Conflict / dedupe rule when two users pull the same ticker** — first-write-wins by `pulled_at_utc`, or prefer `shared_term`? Consumer-side decision.
